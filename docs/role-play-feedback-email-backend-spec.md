# Role Play Feedback Email Backend Spec

## Context

Frontend page:

`https://www.justproveit.co.uk/admin/role-play-feedback`

The page is CRM-authenticated and lets a reviewer complete pension role play feedback. CRM users are split into two groups:

- `A`: is client/reviewer for scenarios `scenario-1`, `scenario-2`, `scenario-3`; is agent for scenarios `scenario-4`, `scenario-5`, `scenario-6`
- `B`: is agent for scenarios `scenario-1`, `scenario-2`, `scenario-3`; is client/reviewer for scenarios `scenario-4`, `scenario-5`, `scenario-6`

The frontend no longer lets the user choose the group manually. It reads the group automatically from the authenticated CRM profile and sends that value as `feedbackGroup`.

For scenarios where the authenticated user is agent, the frontend shows only:

`Scenariul X - esti agent`

No feedback fields or email button are shown.

For scenarios where the authenticated user is client/reviewer, the frontend shows the feedback questions, an `Agent partener` dropdown populated from the opposite group, and a per-scenario send button.

## CRM Profile Group Source

LaunchingStack must add the role play group to the authenticated user profile returned by login/session endpoints.

Preferred response field on the user object:

```json
{
  "user": {
    "id": "user-id",
    "email": "agent@example.com",
    "name": "Agent Name",
    "roles": ["crm-admin"],
    "permissions": ["crm:access"],
    "rolePlayFeedbackGroup": "A"
  }
}
```

Required on:

- `POST /api/auth/login` response, inside `user`
- `GET /api/auth/me` response
- any refresh/session profile response that returns a `user`

Allowed values:

- `A`
- `B`

If a CRM user does not have `rolePlayFeedbackGroup` set to `A` or `B`, the frontend blocks the role play page and shows a setup message.

The frontend also tolerates `user.crmProfile.rolePlayFeedbackGroup`, but `user.rolePlayFeedbackGroup` is the preferred contract.

## Partner Agents Endpoint

Add:

`GET /api/justproveit/admin/role-play-feedback/partner-agents?group=A`

Auth:

`Authorization: Bearer <CRM token>`

`group` is the partner group requested by the frontend:

- if authenticated user profile has `rolePlayFeedbackGroup=A`, frontend requests `group=B`
- if authenticated user profile has `rolePlayFeedbackGroup=B`, frontend requests `group=A`

Backend should validate that the requested group is the opposite of the authenticated user's `rolePlayFeedbackGroup`.

Response:

```json
{
  "success": true,
  "agents": [
    {
      "id": "agent-user-id",
      "name": "Agent Name",
      "email": "agent@example.com",
      "rolePlayFeedbackGroup": "B"
    }
  ]
}
```

Return only active CRM users/agents from the requested group who can receive feedback emails.

## Email Endpoint

Add:

`POST /api/justproveit/admin/role-play-feedback/email`

Auth:

`Authorization: Bearer <CRM token>`

Only CRM/admin users should be allowed to send this email.

Content type:

`application/json`

## Request Payload

The frontend sends:

```json
{
  "tenantKey": "justproveit",
  "source": "pension-role-play-feedback",
  "feedbackGroup": "A",
  "emailScope": "scenario",
  "scenarioId": "scenario-1",
  "partnerAgentId": "partner-agent-user-id",
  "partnerAgentGroup": "B",
  "agentName": "Agent Name",
  "agentEmail": "agent@example.com",
  "reviewerName": "Reviewer Name",
  "reviewerEmail": "reviewer@example.com",
  "sessionDate": "2026-08-19",
  "summary": {
    "totalItems": 5,
    "completedItems": 5,
    "missingItems": 0,
    "yes": 4,
    "partial": 1,
    "no": 0,
    "notApplicable": 0,
    "scorePercent": 90
  },
  "summaryText": "Plain-text ready-to-send summary generated by the frontend.",
  "domain": "www.justproveit.co.uk",
  "pageUrl": "https://www.justproveit.co.uk/admin/role-play-feedback",
  "referrer": "",
  "scenarios": [
    {
      "id": "scenario-1",
      "title": "Scenariul 1 - Calificare, legitimitate si pret",
      "group": "A",
      "participantRole": "client",
      "partnerAgentId": "partner-agent-user-id",
      "partnerAgentName": "Agent Name",
      "partnerAgentEmail": "agent@example.com",
      "partnerAgentGroup": "B",
      "feedbackItems": [
        {
          "id": "registration-number",
          "label": "A mentionat numarul de inregistrare UK (14007642)?",
          "status": "yes"
        }
      ],
      "notes": "Optional scenario notes."
    }
  ]
}
```

For a per-scenario email:

- `emailScope` is `scenario`
- `scenarioId` is present
- `scenarios` contains exactly one scenario
- `summary` and `summaryText` describe that one scenario
- `agentName` / `agentEmail` identify the selected partner agent, not the authenticated reviewer
- `partnerAgentId`, `partnerAgentGroup`, and the scenario-level partner fields identify the same selected partner agent

Allowed `participantRole` values:

- `client`

Allowed feedback item `status` values:

- `yes`
- `partial`
- `no`
- `na`

Allowed `feedbackGroup` values:

- `A`
- `B`

Allowed `emailScope` values:

- `scenario`

## Required Email Behavior

Send one email to `agentEmail`.

Recommended subject:

`Feedback role play pensii - Scenariul {n} - {sessionDate}`

Recommended sender:

Use the existing JustProveIt/CRM Resend sender configuration.

Recommended reply-to:

Use `reviewerEmail` if present and valid.

Email body:

- Greeting with the agent name.
- Include the summary score and counts.
- Include the submitted scenario section.
- Include scenario notes.
- The frontend already provides `summaryText`; backend can use it directly for the plain-text body, or render a nicer HTML email from the structured `scenarios` array.

## Response

Success must only be returned if Resend accepts the send:

```json
{
  "success": true,
  "emailSent": true,
  "message": "Feedback email sent.",
  "result": "resend-message-id"
}
```

Failure examples:

```json
{
  "success": false,
  "emailSent": false,
  "message": "Invalid agent email."
}
```

or return a non-2xx response with a useful `message` or `error.message`.

Important: do not return `success: true` unless a provider message id exists or Resend has accepted the email.

## Validation

Backend should validate:

- `tenantKey` is `justproveit`
- authenticated user has CRM/admin access
- authenticated user's CRM profile has `rolePlayFeedbackGroup` set to `A` or `B`
- `agentEmail` is a valid email
- `agentName`, `reviewerName`, `sessionDate`, `summary`, and `scenarios` are present
- `feedbackGroup` is `A` or `B`
- request `feedbackGroup` matches the authenticated user's CRM profile `rolePlayFeedbackGroup`
- `emailScope` is `scenario`
- `scenarioId` is required and `scenarios` must contain exactly that one scenario
- if `feedbackGroup=A`, only scenario ids `scenario-1`, `scenario-2`, `scenario-3` are accepted for feedback
- if `feedbackGroup=B`, only scenario ids `scenario-4`, `scenario-5`, `scenario-6` are accepted for feedback
- reject submissions for scenarios where the authenticated user is agent
- `partnerAgentId` is present
- `partnerAgentGroup` is the opposite group from authenticated user's `rolePlayFeedbackGroup`
- `agentEmail` matches the selected partner agent's email
- all feedback items have allowed statuses

## Logging

Safe logs may include:

- scenario count
- `feedbackGroup`
- `emailScope`
- `scenarioId`
- partner agent id
- reviewer user id/name
- agent email domain only
- Resend message id
- success/failure code

Do not log full email addresses or the full feedback body unless existing compliance rules allow it.

## Acceptance Criteria

- A CRM-authenticated user can submit completed feedback from `/admin/role-play-feedback`.
- The role play page reads group A/B from the authenticated user profile, not from manual frontend selection.
- If the authenticated CRM profile has no `rolePlayFeedbackGroup`, the frontend blocks sending and shows a setup message.
- Group A submissions can include only scenarios 1/2/3.
- Group B submissions can include only scenarios 4/5/6.
- The evaluated agent can receive one email after each scenario.
- The email is sent to the selected partner agent from the opposite group.
- The frontend receives `success: true` and `emailSent: true` only after Resend accepts the email.
- If Resend/template/email validation fails, the frontend receives a clear failure response and shows the error.
