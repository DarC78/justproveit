# JustProveit Admin Auth Requirements

## Purpose

Extend the shared LaunchingStack Azure Functions auth backend so the JustProveit frontend can safely expose admin-only functionality to approved users.

The current JustProveit login integration supports normal authenticated users, access tokens, refresh tokens, `/auth/me`, and logout. It does not yet expose or enforce tenant-scoped admin permissions.

This document defines the backend requirements needed before the JustProveit frontend can implement an admin area.

## Existing Context

JustProveit tenant details:

- Tenant name: `JustProveit`
- Tenant key: `justproveit`
- Primary domain: `justproveit.co.uk`
- Alternate domain: `www.justproveit.co.uk`

Current shared Functions base URL:

```text
https://launchingstack-func-dev.azurewebsites.net/api
```

Current frontend auth behavior:

- `POST /auth/login` returns `user`, `token`, and `refreshToken`.
- Protected frontend API calls send `Authorization: Bearer <token>`.
- `POST /auth/refresh` rotates the access and refresh tokens.
- `GET /auth/me` restores the current user.
- `POST /auth/logout` revokes the backend session.

## Security Principle

Admin access must be enforced by the backend.

The frontend may hide admin navigation, protect admin routes, and improve UX, but it must not be the security boundary. Every admin API endpoint must validate:

1. The access token is valid.
2. The token belongs to the JustProveit tenant context.
3. The authenticated user has an admin permission for the JustProveit tenant.
4. The requested admin action is allowed for that user's role.

## Required Authorization Model

LaunchingStack should add tenant-scoped role or permission support for users.

Recommended model:

```text
tenant_user_roles
- id
- tenant_id
- user_id
- role
- created_at
- updated_at
- created_by_user_id nullable
```

Minimum required role:

```text
admin
```

Optional future roles:

```text
owner
editor
support
viewer
```

For the first implementation, JustProveit only requires a boolean admin decision:

```text
Is this authenticated user an admin for tenantKey=justproveit?
```

If LaunchingStack already has a tenant membership, user role, claim, or permission table, reuse that existing model instead of adding a new one. The important requirement is that admin status is tenant-scoped and queryable by the auth backend.

## Required User Shape

The login response and `/auth/me` response must expose enough information for the frontend to decide whether to render admin routes.

Recommended shape:

```json
{
  "id": "guid",
  "email": "admin@example.com",
  "name": "Display Name",
  "emailVerified": true,
  "tenantKey": "justproveit",
  "roles": ["admin"],
  "permissions": ["admin:access"]
}
```

Minimum acceptable shape:

```json
{
  "id": "guid",
  "email": "admin@example.com",
  "name": "Display Name",
  "emailVerified": true,
  "tenantKey": "justproveit",
  "isAdmin": true
}
```

The preferred approach is `roles` and/or `permissions`, because it allows future admin permissions without changing the frontend contract.

## JWT Claims

Access tokens should include tenant-scoped admin claims so admin endpoint checks do not depend only on client-provided data.

Recommended JWT claims:

```json
{
  "sub": "user-guid",
  "email": "admin@example.com",
  "tenantKey": "justproveit",
  "tenantId": "tenant-guid",
  "roles": ["admin"],
  "permissions": ["admin:access"]
}
```

Requirements:

- Claims must be generated by the backend from trusted database state.
- Clients must not be able to self-assert admin status in a request body.
- If a user's admin role is removed, newly issued access tokens must no longer contain admin claims.
- Refreshing a session must re-evaluate the user's current roles before issuing the new access token.

## Required Auth Endpoint Changes

### POST `/auth/login`

Current behavior should remain unchanged for normal users.

For admin users, the `user` object should include admin role data.

Successful admin response:

```json
{
  "user": {
    "id": "guid",
    "email": "admin@example.com",
    "name": "Display Name",
    "emailVerified": true,
    "tenantKey": "justproveit",
    "roles": ["admin"],
    "permissions": ["admin:access"]
  },
  "token": "jwt access token",
  "refreshToken": "opaque refresh token"
}
```

Successful non-admin response:

```json
{
  "user": {
    "id": "guid",
    "email": "user@example.com",
    "name": "Display Name",
    "emailVerified": true,
    "tenantKey": "justproveit",
    "roles": [],
    "permissions": []
  },
  "token": "jwt access token",
  "refreshToken": "opaque refresh token"
}
```

### GET `/auth/me`

Must return current role/permission data for the authenticated user.

Response:

```json
{
  "id": "guid",
  "email": "admin@example.com",
  "name": "Display Name",
  "emailVerified": true,
  "tenantKey": "justproveit",
  "roles": ["admin"],
  "permissions": ["admin:access"],
  "createdAt": "2026-04-18T00:00:00.000Z"
}
```

Requirements:

- Response must be based on the authenticated token.
- Response must not accept a user id from the client.
- Response should reflect current database role state, or the current trusted token claims if that is the established LaunchingStack pattern.

### POST `/auth/refresh`

Refresh must preserve the existing response shape while ensuring admin claims are up to date.

Response:

```json
{
  "token": "new jwt access token",
  "refreshToken": "new opaque refresh token",
  "user": {
    "id": "guid",
    "email": "admin@example.com",
    "name": "Display Name",
    "emailVerified": true,
    "tenantKey": "justproveit",
    "roles": ["admin"],
    "permissions": ["admin:access"]
  }
}
```

If returning `user` from refresh would break existing clients, it can be omitted. In that case, the frontend will call `/auth/me` after refresh to update role state.

Requirement:

- Refresh must re-check active tenant role state before issuing a new access token.

## Required Admin Authorization Helper

Add a shared backend helper/middleware for Azure Functions admin checks.

Suggested behavior:

```text
requireTenantAdmin(request, tenantKey)
```

Responsibilities:

- Read and validate `Authorization: Bearer <token>`.
- Resolve the authenticated user.
- Resolve the tenant from the token, request route, or tenant key.
- Check whether the user has an admin role/permission for that tenant.
- Return a consistent `401` or `403` error when unauthorized.

Required status codes:

| Scenario | Status | Response |
| --- | --- | --- |
| Missing token | `401` | `{ "error": "Authentication required" }` |
| Invalid/expired token | `401` | `{ "error": "Invalid or expired token" }` |
| Authenticated but not admin | `403` | `{ "error": "Admin access required" }` |
| Valid admin | Continue | Continue to handler |

## Required Admin Capability Endpoint

Add a lightweight endpoint the frontend can call to confirm admin access.

```http
GET /justproveit/admin/me
Authorization: Bearer <token>
```

On Azure Functions, do not use routes beginning with `/admin/*`; the runtime reserves admin routes and live testing returned `404` for `/api/admin/me`. Use `/api/justproveit/admin/*` instead.

Successful response:

```json
{
  "user": {
    "id": "guid",
    "email": "admin@example.com",
    "name": "Display Name"
  },
  "tenant": {
    "key": "justproveit",
    "name": "JustProveit"
  },
  "roles": ["admin"],
  "permissions": ["admin:access"]
}
```

Non-admin response:

```http
403 Forbidden
```

```json
{
  "error": "Admin access required"
}
```

This endpoint gives the frontend a simple and reliable admin gate before rendering the admin dashboard.

## Admin API Namespace

All future JustProveit admin-only endpoints should live under:

```text
/justproveit/admin/*
```

Examples:

```text
GET /justproveit/admin/me
GET /justproveit/admin/users
GET /justproveit/admin/submissions
PATCH /justproveit/admin/submissions/{id}
GET /justproveit/admin/audit-log
```

Every endpoint under `/justproveit/admin/*` must use the shared admin authorization helper.

## Admin Management Requirements

LaunchingStack should provide one of the following ways to grant and revoke JustProveit admin access.

Preferred option:

```text
Backend-only administrative operation used by LaunchingStack team
```

Required operations:

- Grant `admin` role to a user for `tenantKey=justproveit`.
- Revoke `admin` role from a user for `tenantKey=justproveit`.
- List current JustProveit admins.

The first version does not require a JustProveit frontend UI for managing admins.

## Audit Requirements

Admin-sensitive changes should be auditable.

At minimum, log:

- Role grants.
- Role revocations.
- Failed admin authorization attempts.
- Successful admin actions that change data.

Recommended audit fields:

```text
id
tenant_id
actor_user_id
action
target_type
target_id
metadata_json
ip_address
user_agent
created_at
```

## CORS Requirements

The Functions app must allow requests from:

```text
https://justproveit.co.uk
https://www.justproveit.co.uk
```

Development/staging origins should also be included as needed.

Admin endpoints must support:

```http
Authorization
Content-Type
```

## Frontend Contract Summary

Once LaunchingStack implements this, the JustProveit frontend will rely on:

1. Login and `/auth/me` return either `roles`/`permissions` or `isAdmin`.
2. Admin access can be confirmed with `GET /justproveit/admin/me`.
3. Admin-only API calls return `401` for unauthenticated users.
4. Admin-only API calls return `403` for authenticated non-admin users.
5. Refresh tokens issue access tokens with current role claims.

Preferred frontend admin check:

```js
const isAdmin =
  user?.roles?.includes("admin") ||
  user?.permissions?.includes("admin:access");
```

Acceptable fallback:

```js
const isAdmin = user?.isAdmin === true;
```

## Acceptance Criteria

- A normal JustProveit user can log in and use existing authenticated functionality.
- A normal JustProveit user receives `403` from `GET /justproveit/admin/me`.
- A JustProveit admin receives `200` from `GET /justproveit/admin/me`.
- Login response for an admin includes admin role/permission data.
- `/auth/me` response for an admin includes admin role/permission data.
- Refreshing an admin session returns a token that preserves current admin claims.
- Removing admin access prevents future refreshed tokens from containing admin claims.
- All `/justproveit/admin/*` endpoints reject missing, invalid, expired, or non-admin tokens.
- Admin role grants and revocations are auditable.
- CORS allows the JustProveit frontend domains to call auth and admin endpoints.

## Open Decisions For LaunchingStack

- Whether to expose `roles`, `permissions`, `isAdmin`, or a combination.
- Whether admin roles are stored in an existing membership table or a new tenant role table.
- Whether `/auth/refresh` returns an updated `user` object or the frontend should call `/auth/me` after refresh.
- Which admin data endpoints JustProveit needs after the initial `/justproveit/admin/me` gate.
- Whether LaunchingStack wants an internal admin management UI or backend-only scripts/operations for the first release.
